## 0. 선수 지식 정리

- **블록 암호**: 평문을 고정 크기 블록(DES 64bit, AES 128bit)으로 잘라 블록 단위로 암호화. **스트림 암호**: 키로 만든 키스트림을 평문과 비트/바이트 단위로 XOR.
- **대칭키의 가장 큰 문제는 키 분배**: 통신 전에 같은 키를 안전하게 공유해야 하고, 아니면 KDC를 둬야 하는데 KDC가 뚫리면 전체가 위험. 디지털 서명에도 쓰기 어려움. → 공개키 암호가 나온 배경.
- **Feistel 구조**: 블록을 L, R로 나눠 `L' = R`, `R' = L ⊕ F(R, 라운드키)`. 복호화는 같은 구조에 라운드키를 역순으로 넣으면 됨(F의 역함수 불필요). DES가 이 구조, AES는 아님.
- `17 mod 5 = 2`. **서로소**는 `gcd(a,b)=1` (8과 15는 서로소, 8과 12는 gcd 4라 아님).
- 소수 두 개의 곱은 쉽지만 곱 n에서 p, q를 되찾는 건 n이 커질수록 계산량이 폭발적으로 늘어남(1024bit면 사실상 불가능). RSA 안전성의 뿌리이자 one-way function의 전형적 예.

## 1. Block Cipher Modes of Operation *(p.3~11)*

**Mode of operation**: 블록 암호는 한 블록만 암호화할 수 있어서, 긴 메시지를 여러 블록에 걸쳐 어떻게 적용할지 정해놓은 방식.

- 모드는 ECB, CBC, CFB, OFB, CTR 5가지. 이 강의는 **ECB와 CTR**만 다룸.

### ECB (Electronic Codebook) *(p.5~7)*

**ECB**: 평문을 블록으로 나눠 각 블록을 같은 키로 독립적으로 암호화하는 가장 단순한 모드.

```
암호화: Cᵢ = Encrypt_K(Pᵢ)
복호화: Pᵢ = Decrypt_K(Cᵢ)
```

- 이름이 "코드북"인 이유: 같은 키 아래에서 평문 블록 ↔ 암호문 블록이 일대일 대응하는 거대한 사전 같기 때문.
- 블록끼리 서로 영향을 주지 않음.
- **적합한 용도**: 암호화 키 같은 짧은 데이터
- **약점**: 같은 평문 블록은 항상 같은 암호문 블록 → 긴 메시지에서 반복 패턴이 그대로 드러남.

Q&A — 3번째와 7번째 평문 블록이 같으면? 암호문 블록도 같아짐 → 빈도분석 가능. 추가로:
- 블록이 평문과 일대일 대응해서, 자주 나오는 블록의 의미(헤더, 공백, 특정 필드)를 추측하면 그 블록이 나오는 모든 위치를 알아낼 수 있음.
- 블록끼리 독립이라 블록 삭제/순서 바꿔치기를 해도 복호화가 정상적으로 되고 눈치채기 어려움.
- 이미지는 같은 색 영역이 같은 암호문 블록이 돼서 윤곽이 그대로 보임.
- 그래서 ECB는 키처럼 짧고 예측 불가능한 데이터에만 쓰고, 긴 메시지엔 다른 모드를 씀.

### CTR (Counter) Mode *(p.8~11)*

**CTR**: 블록마다 다른 카운터 값을 암호화해서 키스트림처럼 만들고, 이를 평문과 XOR해서 암호문을 만드는 모드.

```
암호화: Cᵢ = Pᵢ ⊕ Encrypt_K(Counter + i)
복호화: Pᵢ = Cᵢ ⊕ Encrypt_K(Counter + i)
```

- 카운터를 초깃값에서 시작해 블록마다 1씩 증가. SP 800-38A는 카운터 값이 평문 블록마다 달라야 한다고 요구.
- 평문 자체는 블록 암호에 들어가지 않고 카운터만 암호화됨. 블록 암호를 스트림 암호처럼 쓰는 셈.
- 복호화도 `Encrypt`를 씀. 같은 키스트림을 다시 XOR하면 평문이 돌아옴(`A ⊕ B ⊕ B = A`).
- ATM 네트워크 보안, IPSec에서 쓰임이 늘고 있음.

**장점 6가지** *(p.10~11)*
1. **Hardware efficiency**: 블록 간 의존성이 없어 병렬 처리 가능
2. **Software efficiency**: 병렬 처리를 지원하는 프로세서를 잘 활용
3. **Preprocessing**: `Encrypt_K(Counter+i)`는 평문과 무관해서 미리 계산 가능. 평문이 도착하면 XOR만 하면 됨
4. **Random access**: i번째 블록만 앞 블록 없이 바로 처리 가능
5. **Provable security**: 다른 모드들만큼 안전함이 증명됨
6. **Simplicity**: 암호화 알고리즘만 구현하면 됨. 복호화 알고리즘과 복호화용 key scheduling 불필요

Q&A — 같은 평문 블록이 3번째와 7번째에 있으면? 카운터가 달라 `Encrypt_K(Counter+i)`가 매번 다른 키스트림 조각이 되므로 암호문이 서로 달라짐 → ECB의 패턴 노출 약점 해결.
- 주의: **같은 키로 카운터 값이 한 번이라도 재사용되면** 키스트림이 같아져서 두 암호문을 XOR하면 키스트림이 지워지고 평문끼리의 XOR이 드러남. 슬라이드가 카운터가 매 블록 달라야 한다고 못박은 이유.

## 2. AES *(p.13~15)*

**AES (Advanced Encryption Standard)**: NIST가 2001년 11월 26일 FIPS PUB 197로 발표한, Feistel 구조가 아닌 128bit 블록 대칭 블록 암호.

### 스펙 *(p.13)*

| 항목 | 값 |
|---|---|
| 블록 크기 | 128 bit |
| 키 크기 | 128 / 192 / 256 bit |
| 라운드 수 | 10 / 12 / 14 (키 크기에 대응) |

- DES(64bit 블록, 56bit 키)보다 블록도 키도 커짐.
- Feistel은 블록을 반으로 나눠 한쪽만 바꾸는데, AES는 **라운드마다 128bit 전체를 한꺼번에 변환**.

### 전체 구조 *(p.14~15)*

- 데이터 블록(128bit = 16바이트)을 **4×4 바이트 행렬, 즉 state**로 취급.
- 키는 **word 배열로 확장(key expansion)**되어 라운드마다 다른 라운드키 사용.

**한 라운드의 4가지 연산**
1. **Byte substitution (SubBytes)**: state의 모든 바이트에 S-box 하나를 적용해 바이트 단위 치환
2. **Shift rows**: 행마다 바이트를 옆으로 밀어 열 사이에서 바이트를 섞음
3. **Mix columns**: 열 단위 행렬곱으로 한 열의 바이트들이 서로 영향을 주게 함
4. **Add round key**: state와 라운드키를 XOR

- **키를 쓰는 건 Add round key뿐**. 나머지 셋은 키 없이 데이터를 뒤섞는 역할 → 전체적으로 "키와 XOR → 데이터 뒤섞기"가 번갈아 반복.
- 암호 이론으로: SubBytes가 입력-출력 관계를 복잡하게 만드는 혼돈(confusion), Shift rows와 Mix columns가 한 바이트의 변화를 state 전체로 퍼뜨리는 확산(diffusion)을 담당.
- **특이점**: 첫 라운드 전에 **초기 XOR(키 material)**이 한 번 있고, **마지막 라운드는 불완전**(Mix columns 생략).

```
평문 → [초기 Add round key] → Round 1 → ... → Round 9 → Round 10(Mix columns 없음) → 암호문
```

- 라운드키는 확장된 키 w[0,3], w[4,7], ..., w[40,43]을 4 word(=128bit)씩 사용. 초기 XOR에 w[0,3], Round 10에 w[40,43].
- **복호화**는 같은 라운드키를 역순으로 쓰며 inverse sub bytes, inverse shift rows, inverse mix columns 적용.
- 빠른 XOR와 테이블 조회로 구현 가능 → 소프트웨어·하드웨어 모두 효율적.

Q&A — Feistel(DES)과의 가장 큰 구조 차이: Feistel은 블록을 반으로 나눠 라운드마다 한쪽만 변환, AES는 라운드마다 **한 블록(128bit) 전체**를 변환(SubBytes는 모든 바이트에, Mix columns는 모든 열에). 한 라운드만 지나도 변화가 state 전체로 퍼져서 라운드 수를 10 정도로 적게 쓸 수 있음.
- "반복 연산 + 재배열로 빈도를 숨긴다"는 AES가 하는 일의 효과(혼돈/확산)이지 Feistel과의 구조 차이는 아님. DES도 라운드를 반복함.

## 3. Public Key Cryptography, RSA *(p.17~49)*

### (A) 왜 필요한가 *(p.18)*
- **키 분배 문제**: 키를 미리 공유하거나 KDC를 써야 하고, KDC가 뚫리면 전체가 위험.
- **디지털 서명 곤란**: 같은 키를 양쪽이 아는 구조라서 누가 만들었는지 제3자에게 증명하기 어려움.

### 공개키 암호의 원리 *(p.19~26)*

**Public-key cryptosystem**: 암호화와 복호화에 서로 다른 두 개의 키(공개키, 개인키)를 쓰며, 공개키와 알고리즘을 알아도 개인키를 계산으로 알아내는 것이 불가능하도록 만든 암호 체계.

- **6가지 구성요소** *(p.20)*: 평문, 암호화 알고리즘, 암호문, 복호화 알고리즘, 공개키, 개인키
- 보통 공개키로 암호화, 개인키로 복호화. RSA 같은 일부 알고리즘은 어느 쪽 키로 암호화해도 다른 쪽 키로 복호화됨.

**사용 절차** *(p.21)*
1. 각자 공개키/개인키 쌍 생성
2. 공개키는 공개 register에 게시, 개인키는 비밀 유지
3. Bob이 Alice에게 보낼 땐 **Alice의 공개키**로 암호화
4. Alice는 **자신의 개인키**로 복호화

| 용도 | 암호화에 쓰는 키 | 복호화에 쓰는 키 | 제공하는 것 |
|---|---|---|---|
| 비밀성 *(p.22)* | 수신자의 공개키 | 수신자의 개인키 | 수신자만 읽을 수 있음 |
| 인증 *(p.24)* | 송신자의 개인키 | 송신자의 공개키 | 송신자만 만들 수 있음(누구나 읽을 수 있어 비밀성은 없음) |
| 둘 다 *(p.26)* | A의 개인키(PRa) 후 B의 공개키(PUb) | B의 개인키(PRb) 후 A의 공개키(PUa) | 인증 + 비밀성 |

**응용 분야** *(p.27)*: 암복호화(비밀성), 디지털 서명(인증), 키 교환(세션키 교환). RSA와 Elliptic Curve는 세 가지 모두, Diffie-Hellman은 키 교환만, DSS는 디지털 서명만 지원.

Q&A
- 인증 용도가 비밀성을 못 주는 이유: 개인키로 암호화한 건 공개키로 복호화되는데, 공개키는 누구나 가지고 있으므로 아무나 읽을 수 있음.
- Bob이 Alice에게 "Alice만 읽을 수 있고 Bob이 보낸 게 확실한" 메시지를 보내려면: 키는 **쌍으로만** 작동(어떤 키로 암호화하면 그 짝 키로만 복호화). 암호화는 ① Bob의 개인키(인증) → ② Alice의 공개키(비밀성). 복호화는 양파 껍질 벗기듯 **바깥 겹부터**: ① Alice의 개인키 → ② Bob의 공개키. 가장 바깥 겹이 Alice의 공개키라서 Alice의 개인키가 먼저.
- 슬라이드 표기: `X → E(PUa, E(PRb, X))`로 보내고, A는 `D(PUb, D(PRa, ·))`로 복원.

### (B) 요구사항과 trap-door *(p.28~32)*

Diffie와 Hellman의 조건 (A가 B에게 보내는 상황):
1. B가 공개키/개인키 쌍을 **쉽게 생성**
2. A가 B의 공개키로 `C = E_KUb(M)`을 **쉽게 계산**
3. B가 개인키로 `M = D_KRb(C)`를 **쉽게 계산**
4. 공격자가 공개키 KUb만 알고 개인키 KRb를 알아내는 건 **infeasible**
5. 공격자가 KUb와 암호문 C만 알고 평문 M을 복원하는 것도 **infeasible**
6. (선택) 적용 순서를 바꿔도 같아야 함: `M = E_KUb[D_KRb(M)] = D_KUb[E_KRb(M)]` → "인증" 용도가 가능해지는 조건

요구사항이 까다로워서 실제로 널리 쓰이는 건 **RSA**와 **elliptic curve cryptography** 정도 *(p.30)*.

**One-way function**: 순방향 `Y = f(X)`는 쉽지만 역방향 `X = f⁻¹(Y)`는 계산적으로 불가능에 가까운 함수. *(p.31)*
- "easy"는 다항 시간에 풀린다는 뜻, "infeasible"은 최악/평균이 아니라 **거의 모든 입력에서** 역산이 어렵다는 뜻.
- 예: 두 소수의 곱은 쉽지만 소인수분해는 어려움.

**Trap-door one-way function**: 역방향도 **추가 정보(trapdoor, k)를 알면 쉽게** 계산되고, 모르면 infeasible한 one-way function. *(p.32)*

```
Y = f_k(X)      : k와 X를 알면 쉬움
X = f_k⁻¹(Y)    : k와 Y를 알면 쉬움
X = f_k⁻¹(Y)    : Y만 알고 k를 모르면 infeasible
```

- 실용적인 공개키 스킴을 만드는 일은 결국 적당한 trap-door one-way function을 찾는 문제.

### 공개키 암호 공격 *(p.33~34)*

| 공격 | 내용 | 대응 |
|---|---|---|
| Brute-force (개인키 대상) | 가능한 개인키를 전부 시도 | 큰 키 사용. 단, 실용적인 암복호화가 가능한 크기여야 함 |
| 공개키로 개인키 직접 계산 | 수학적으로 역산 | 아직 이 공격에 안전함이 **증명된** 알고리즘은 없음 |
| Probable-message attack | 메시지가 제한된 후보값(예: 56bit DES 키)이면 후보를 전부 공개키로 암호화해 암호문과 대조 | 큰 키 크기, 메시지에 임의 비트 덧붙이기 |

Q&A
- Probable-message attack이 공개키 암호에만 위협인 이유: 공개키는 누구나 알아서 공격자가 후보를 직접 암호화해볼 수 있음. 대칭키는 공격자에게 키가 없어서 못 함. 임의 비트를 덧붙이면 같은 후보도 매번 다른 값이 되어 후보 집합이 커져 대조가 불가능해짐.
- "개인키는 공개키를 함수에 넣은 결과인가?" → 아니, 방향이 반대. 개인키와 공개키는 **키 생성 단계에서 같이 만들어지고**, 개인키(trapdoor 정보)를 가진 쪽이 공개키를 쉽게 만들 수 있음. **공개키만 보고 개인키를 구하는 것**이 요구사항 4번의 infeasible한 방향. 공개키로 개인키가 나오는 함수가 있다면 그게 곧 공격 방법.

### (C) RSA 알고리즘 *(p.35~45)*

**RSA**: 1977년 Rivest, Shamir, Adleman이 만든, 큰 수의 소인수분해 어려움에 기반한 공개키 블록 암호.

- 평문/암호문은 `0 ~ n-1` 정수, n은 보통 1024bit(약 309자리), `n = pq` *(p.35)*
- 블록 크기 k bit, `2^k < n ≤ 2^(k+1)` *(p.36)*

```
암호화: C = M^e mod n
복호화: M = C^d mod n = (M^e)^d mod n = M^(ed) mod n
공개키 = {e, n}     개인키 = {d, n}
```
*(p.37)*

복호화가 되려면 `M^(ed) ≡ M (mod n)`이어야 하고, 이를 보장하는 게 **오일러 정리**.

**Euler's theorem 따름정리** *(p.40)*: 소수 p, q, `n = pq`, `0 < m < n`, 임의의 정수 k에 대해 `m^(kΦ(n)+1) ≡ m mod n` (`Φ(n) = (p-1)(q-1)`)
- **Φ(n)**: 오일러 totient 함수. n보다 작고 n과 서로소인 양의 정수의 개수. n이 두 소수의 곱이면 `(p-1)(q-1)`.
- `ed = kΦ(n)+1`이 되게 e, d를 고르면 됨. 즉 `ed ≡ 1 mod Φ(n)`, `d ≡ e⁻¹ mod Φ(n)`.
- 역원이 존재하려면 **e가 Φ(n)과 서로소**여야 함(`gcd(Φ(n), e) = 1`). *(p.41)*

**RSA 재료** *(p.42)*

| 값 | 공개 여부 | 어떻게 정해지나 |
|---|---|---|
| p, q (소수) | 비공개 | 직접 선택 |
| n = pq | 공개 | 계산 |
| e (`1<e<Φ(n)`, `gcd(Φ(n),e)=1`) | 공개 | 선택 |
| d ≡ e⁻¹ mod Φ(n) | 비공개 | 계산(extended Euclid) |

- trapdoor: **p, q를 알면 Φ(n)을 알고 d를 계산할 수 있고, n만 알면 p, q를 몰라 d를 구할 수 없음.**
- 동작 *(p.43)*: B가 A에게 M을 보낼 때 A의 공개키 `{e,n}`으로 `C = M^e mod n` 전송 → A는 개인키 `{d,n}`으로 `M = C^d mod n`.

**수치 예시** *(p.44~45)*
```
p=17, q=11  →  n = 187,  Φ(n) = 16×10 = 160
e = 7 (160과 서로소)
d: de ≡ 1 mod 160 → d = 23   (7×23 = 161 = 160+1)

암호화: 평문 88 → 88^7 mod 187 = 11
   88^1=88, 88^2=77, 88^4=132 (mod 187)
   88^7 = 88^4 × 88^2 × 88^1 → (88×77×132) mod 187 = 894,432 mod 187 = 11

복호화: 11^23 mod 187 = 88
   11^1=11, 11^2=121, 11^4=55, 11^8=33
   11^23 = (11×121×55×33×33) mod 187 = 79,720,243 mod 187 = 88
```
- 거듭제곱은 한 번에 계산하지 않고 **제곱을 반복해(square-and-multiply) 지수를 이진 분해**해 곱함. 큰 지수도 빠르게 계산됨.

Q&A — 공격자가 `n=187`, `e=7`, 암호문 `11`을 알 때 d를 구하려면: 먼저 **Φ(n)**이 필요(`d ≡ e⁻¹ mod Φ(n)`이므로 알면 extended Euclid로 d 계산). `Φ(n) = (p-1)(q-1)`이라 p, q가 필요 → **n을 소인수분해**해야 함(187 = 11×17). 예시는 원리 확인용이고 실제 n은 1024bit 이상이라 분해가 사실상 불가능.
- 역방향도 성립: Φ(n)을 알면 `n = pq`와 `p+q = n - Φ(n) + 1`로 p, q를 구할 수 있어서, Φ(n)을 아는 것과 n을 분해하는 건 동등한 난이도(수학적 공격 2번).

### The Security of RSA *(p.46~49)*

공격 3가지: **Brute force, Mathematical attacks, Timing attacks**

- **Brute force**: 가능한 개인키를 전부 시도. 대응책은 큰 키 공간. 키가 클수록 암복호화도 느려지니 타협이 필요.
- **Mathematical attacks** *(p.47)*: 세 접근의 난이도는 사실상 같음
  1. n을 두 소인수로 분해 → Φ(n)과 d 계산
  2. p, q를 거치지 않고 Φ(n)을 직접 알아냄(n 분해와 동등)
  3. Φ(n)을 거치지 않고 d를 직접 알아냄(현재 알려진 알고리즘으로는 factoring만큼 걸림)
  → **RSA의 안전성은 n의 소인수분해 난이도에 달려 있음.**
- **소인수분해 기록** *(p.48)*: 자릿수가 늘수록 필요한 계산량(MIPS-years)이 기하급수적으로 증가. 100자리는 1991년 7 MIPS-years, 200자리는 2005년 lattice sieve로 해결. 컴퓨팅 능력과 알고리즘이 발전하므로 RSA는 시간이 갈수록 더 큰 키를 요구.
- **p, q 선택 제약** *(p.49)*: n이 쉽게 분해되지 않도록
  - p와 q는 길이가 비슷해야 함(몇 자리 이상 차이나면 안 됨)
  - `p-1`과 `q-1` 모두 큰 소인수를 포함해야 함
  - `gcd(p-1, q-1)`은 작아야 함
  - `e < n`이고 `d < n^(1/4)`이면 d를 쉽게 알아낼 수 있음이 증명됨 → d가 너무 작으면 안 됨
- **Timing attacks**: 슬라이드에는 이름만 나옴. 복호화 시간이 개인키 값에 따라 달라지는 점을 이용한 공격.

Q&A — p, q가 비슷한 길이여야 하는 이유: 소인수분해는 작은 수부터 나눠보는 trial division 같은 방법으로 시작해도 **작은 소인수는 초반에 바로 걸림**. n이 아무리 커도 p가 작으면 금방 분해되고, 그러면 q = n/p, Φ(n), d가 연달아 나옴. 안전성은 n의 크기가 아니라 **두 소인수 중 작은 쪽의 크기**가 결정.
- 슬라이드는 길이가 몇 자리 이상 차이나면 안 된다는 것까지만 말함. 반대로 p와 q가 **너무 가까운 것도** 약점(슬라이드 밖 지식: Fermat 인수분해가 √n 근처에서 바로 찾아냄). 그래서 "비슷하되 너무 가깝지는 않게"가 정확.

## 4. One-way Hash Functions *(p.50~55)*

**One-way hash function**: 임의 길이의 메시지를 고정 크기의 값으로 압축하되, 결과로 원문을 되돌리거나 같은 결과를 내는 다른 입력을 찾는 것이 계산적으로 불가능한 함수. *(p.51)*

```
h = H(M)       예) SHA1("The quick brown fox jumps over the lazy cog") = 0xde9f2c7f...
```

- 보통 해시 함수는 **공개되어 있고 키가 없다(unkeyed)**고 가정. 키가 있는 건 MAC.
- 메시지 변경 탐지에 해시를 활용한 것이 **HMAC**.
- 용도: 비밀번호 저장, 고유 file_id 생성, 가장 흔하게는 **디지털 서명 생성**.

### 요구사항 6가지 *(p.52)*

| # | 요구사항 | 이름 |
|---|---|---|
| 1 | 임의 크기의 M에 적용 가능 | |
| 2 | 고정 길이 출력 h | |
| 3 | `h = H(M)` 계산이 쉬움 | easy to compute |
| 4 | 주어진 h에 대해 `H(x) = h`인 x를 찾는 것이 infeasible | **one-way property** |
| 5 | 주어진 x에 대해 `H(y) = H(x)`인 y를 찾는 것이 infeasible | **weak collision resistance** |
| 6 | 임의의 쌍 `x, y`로 `H(y) = H(x)`를 찾는 것이 infeasible | **strong collision resistance** |

- 5번과 6번의 차이는 **x가 고정되어 있느냐**. 5번은 정해진 x와 충돌하는 y를 찾는 것, 6번은 x, y를 둘 다 마음대로 고를 수 있어 더 쉬운 문제. 6번을 만족하면 5번도 만족.
- 입력은 무한한데 출력은 고정 길이라 충돌은 반드시 존재. 요구사항은 그걸 **찾기 어렵다**는 것.

### 응용 *(p.53)*
Message Authentication Code(MAC), 비밀번호 저장, Digital Signature

### 표준 해시와 Birthday Attack *(p.54~55)*

표준 해시 함수: MD5, SHA-1, SHA-256/384/512, RIPEMD160 (세부 알고리즘은 생략).

**Birthday Attack**: 생일 역설을 이용해, 해시 길이의 절반 정도 비트에 해당하는 수의 메시지만 만들어도 충돌을 찾을 수 있는 공격.

해시 길이가 m bit일 때:
1. 공격자가 **정상 메시지의 변형 `2^(m/2)`개**와 **위조 메시지의 변형 `2^(m/2)`개**를 만듦
2. 두 집합에서 **해시값이 같은 쌍**을 찾음. 생일 역설 때문에 존재할 확률이 0.5 초과
3. 정상 메시지 쪽에 서명을 받음
4. 서명은 해시에 붙어 있으므로 **같은 해시를 가진 위조 메시지로 바꿔치기**해도 유효한 서명처럼 보임

- 64bit 해시면 `2^64`번이 아니라 `2^32`번 정도로 충분. 그래서 **더 긴 해시/MAC**을 써야 함.

Q&A
- birthday attack이 깨는 요구사항: **6번 strong collision resistance** (x, y를 둘 다 공격자가 고르는 문제).
- 왜 `2^(m/2)`인가: 한 값(h)에 맞추는 건 후보를 그 값과 비교하니 `2^m`번 필요. 반면 충돌은 **아무 두 개나 같으면 성공**이라 메시지 N개면 비교 가능한 쌍이 `N(N-1)/2`개, 즉 N²에 비례해 늘어남. 쌍의 수가 `2^m`쯤 되면 충돌이 나오니 `N² ≈ 2^m`, `N ≈ 2^(m/2)`. 23명만 모여도 생일이 같은 쌍이 있을 확률이 50%를 넘는 것과 같은 원리.
- 일반 무차별 대입(주어진 h에 맞는 x 찾기)은 **4번 one-way property**를 노리는 공격, 주어진 x에 대해 y를 찾는 건 5번.
- 4, 5번이 안 깨졌더라도 6번이 먼저 무너질 수 있어서 해시 길이는 6번 기준으로 잡아야 함. m bit 해시의 실질 안전도는 m/2 bit 수준.

## 5. Digital Signatures *(p.56~62)*

**Digital signature**: 메시지 내용과 서명자를 인증하는 것에서 나아가, 제3자가 검증해서 분쟁을 해결할 수 있게 해주는, 서명자의 개인키로 만든 값. *(p.57)*

### 목적 *(p.57)*
인증에 더해 다음을 제공.
- 메시지 내용 인증
- 서명자와 서명 일시 검증
- **제3자가 검증해서 분쟁을 해결**할 수 있음

→ 일반 MAC과의 핵심 차이. MAC은 키를 양쪽이 공유하니 둘 중 누가 만들었는지 제3자에게 증명할 수 없음. 서명은 개인키가 서명자 한 명에게만 있어서 증명이 됨.

### 디지털 서명이 가져야 할 성질 *(p.58~59)*
- 서명은 **서명 대상 메시지에 의존하는 bit pattern**이어야 함
- **서명자에게 고유한 정보**를 써야 함 → 위조(forgery)와 부인(denial) 모두 방지
- 서명 생성이 비교적 쉬워야 함
- 서명의 인식/검증이 비교적 쉬워야 함
- 서명 사본을 저장해두는 것이 실용적이어야 함
- **계산적으로 위조가 불가능**해야 함(기존 서명에 맞는 새 메시지를 만들거나, 주어진 메시지에 대한 사기 서명을 만드는 것 모두 불가능)

### Direct Digital Signature *(p.61)*
- **가정**: 송신자와 수신자만 관여하고, 수신자가 송신자의 공개키를 알고 있음
- **서명 방법**(셋 중 하나): ① 메시지 전체를 개인키로 암호화 ② 해시를 계산한 뒤 **해시값을 개인키로 암호화** ③ 전용 서명 생성 알고리즘 사용
- **문제점**: 위 가정을 현실에서 어떻게 만족시키는지, 송신자가 개인키를 분실하면 어떻게 되는지 등. 슬라이드에서는 Chapter 14에서 다룬다고 하고 스킵.

### RSA Digital Signature *(p.62)*

**방법 1 (단순)**: `E_KRa(M)`. 메시지 전체를 A의 개인키로 암호화하고 B가 A의 공개키로 복호화. 앞의 "인증" 용도 그대로이나 긴 메시지 전체를 RSA로 처리하면 느림.

**방법 2 (실용적, 해시 기반)**:
1. A가 메시지 M의 해시 `H(M)`을 계산
2. A가 **해시값만** 자신의 개인키로 암호화해 서명 `E_KRa[H(M)]` 생성
3. 원본 M과 서명을 **함께 전송**
4. B가 받은 M을 직접 해시하고, 서명을 A의 공개키로 복호화한 값과 **비교(Compare)** → 같으면 valid, 다르면 invalid

**3단계 흐름**: ① Signature Creation → ② Send Message(원본 + 서명) → ③ Signature Verification

- 해시를 쓰는 이유: 짧은 고정 길이라 RSA 연산이 가볍고, 해시가 메시지 변경에 민감해 메시지가 바뀌면 검증이 실패.
- 섹션 4의 birthday attack이 여기서 의미를 가짐. 서명이 **해시에 붙어 있는** 구조라 해시 충돌이 곧 서명 위조로 이어짐.

Q&A
- Eve가 M을 M'으로 바꿔치기하면: B는 받은 M'을 직접 해시해 `H(M')`을 얻고, A의 공개키로 서명을 복호화하면 원래 `H(M)`이 나옴. 해시의 one-way/collision resistance 덕분에 `H(M') ≠ H(M)`이라 비교에서 **invalid**. Eve가 서명도 새로 만들려면 A의 개인키가 필요해서 못 함. 예외는 birthday attack으로 `H(M') = H(M)`인 M'을 찾아낸 경우.
- 비밀성은 제공되지 않음: M이 평문으로 같이 전송되고 서명도 A의 공개키로 누구나 복호화 가능. 서명은 **인증, 무결성, 부인방지**를 주며, 비밀성이 필요하면 수신자의 공개키로 한 번 더 암호화해야 함.
